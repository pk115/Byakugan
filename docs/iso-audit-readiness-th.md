# วิเคราะห์ความพร้อมหลักฐานออดิต ISO/IEC 27001 และ Excel รวมไฟล์เดียว

ประเมินจากโค้ดและการทดสอบ Byakugan ณ 11 พฤศจิกายน 2026 ไม่ได้ตรวจฐานข้อมูล Production, CMDB, SoA หรือเอกสารจริงขององค์กร จึงยังสรุปไม่ได้ว่ามีหลักฐานครบหรือผ่านการรับรอง

ISO/IEC 27001 ครอบคลุมระบบบริหารความมั่นคงปลอดภัยสารสนเทศและการบริหารความเสี่ยง ทั้งคน นโยบาย และเทคโนโลยี ข้อมูล Monitoring เป็นหลักฐานสนับสนุนบางส่วน ต้องเทียบขอบเขต ISMS, ความเสี่ยง และ Statement of Applicability (SoA) ที่องค์กรอนุมัติ รายการด้านล่างเป็นการวิเคราะห์ช่องว่าง ไม่ใช่เช็กลิสต์รับรองครบทุกข้อกำหนด

## สิ่งที่ระบบรองรับแล้ว และข้อจำกัด

| เรื่อง | หลักฐานที่ดึงได้ | ยังต้องตรวจหรือเพิ่ม |
|---|---|---|
| สินทรัพย์เซิร์ฟเวอร์ | Agent ID, Hostname, OS, CPU, RAM, Inventory, เวลาส่งข้อมูล | เทียบกับ CMDB ว่าเครื่องครบ; เจ้าของสินทรัพย์ การจัดชั้นข้อมูล และประวัติเปลี่ยนผู้รับผิดชอบยังไม่ครบระดับ Host |
| Capacity และ Availability | CPU/RAM, Disk/Container JSON, Monitor checks, Latency, Database metrics | ตรวจรอบเก็บและช่วงข้อมูลขาด; หลักฐานเฉพาะเครื่องที่ติดตั้งหรือ Monitor ที่ตั้งไว้; Health Check ไม่ใช่หลักฐาน SLA ที่รับรองโดยอิสระ |
| แพตช์และช่องโหว่ | จำนวนแพตช์ค้าง, Reboot flag, CVE/Package/Severity, Scan jobs/results, สถานะ ผู้รับผิดชอบ กำหนดแก้และยอมรับความเสี่ยง | ไม่มีผลสแกนไม่เท่ากับปลอดภัย; ตรวจ Target/Scanner ครอบคลุมจริง, แผนสแกน, SLA การแก้, ผู้อนุมัติ Risk acceptance; Inventory มีจำนวน Package ไม่ใช่รายชื่อซอฟต์แวร์ครบ |
| Logging และ Monitoring | Normalized logs, แหล่งข้อมูล ผู้ใช้ IP ผลลัพธ์ เวลาเกิด/รับ, Health policies/state/history | ต้องยืนยันว่าเปิดเก็บจริงครบทุกเครื่องและแหล่ง Windows/Linux/Firewall/VPN/DB, สิทธิ์อ่าน Log, ความต่อเนื่องและ Clock/NTP; ข้อมูลนอก Retention หรือถูกล้างกู้จากไฟล์นี้ไม่ได้ |
| Incident และ Corrective action | Incident, Severity, Root cause, Corrective action, Lessons learned, Review/Close | ต้องกรอกและตรวจอนุมัติจริง รวม Timeline, ผู้รับผิดชอบ, ผลทดสอบหลังแก้ และการป้องกันเกิดซ้ำ; ปิดเคสไม่ยืนยันว่าบริการฟื้นตัว |
| Backup และ Restore | สถานะงาน ขนาด Checksum เวลาสำรอง และ Restore test/RTO actual | SUCCESS ไม่รับรองว่า Restore ได้; ต้องมีผลทดสอบ ครอบคลุมระบบสำคัญ ผู้อนุมัติ และ RPO/RTO; ปัจจุบันยังไม่มี Agent/Monitor FK ที่ระบุเจ้าของ Backup โดยตรง |
| ความตรวจสอบย้อนหลัง | Audit chain, Metadata การ Export, SHA-256 ไฟล์ และประวัติล้าง/รีเซ็ต | Hash chain ที่ valid ไม่รับรองว่าไม่เคยล้างหลักฐานประเภทอื่น และไม่ใช่ลายเซ็นอิสระ; ต้องกำหนด Retention, สิทธิ์ลบ, สำรองนอกเครื่อง และ Immutable storage ตามนโยบาย |
| Control mapping | Monitor เชื่อม ISO control พร้อม Evidence note | เป็น Mapping ที่ผู้ใช้ตั้ง ไม่ใช่ SoA ทั้งองค์กร; ยังไม่มี Mapping ระดับ Agent และไม่อนุมานผ่านจากจำนวน Mapping |

## หลักฐานที่ต้องจัดจากกระบวนการหรือระบบอื่น

1. ขอบเขต ISMS, นโยบาย, Risk register, Risk assessment/treatment, SoA และการอนุมัติ
2. บัญชีและสิทธิ์ OS/AD/Cloud/Database, การขอสิทธิ์/ทบทวนสิทธิ์, กระบวนการเข้า-ย้าย-ออกงาน และ MFA — บัญชีใน Byakugan ไม่ใช่บัญชีบนเซิร์ฟเวอร์ทั้งหมด
3. Change request/approval, Config baseline/hardening, Firewall/Network configuration, ผลทดสอบและแผน Rollback
4. BCP/DR, RPO/RTO ที่อนุมัติ และผลซ้อมกู้คืน/ความต่อเนื่อง พร้อมการทบทวน
5. การอบรม/ความสามารถ, คู่ค้า/สัญญา, ภาระหน้าที่ตามข้อกำหนด และการควบคุมทางกายภาพตามขอบเขต
6. แผนออดิตภายใน ผลออดิต Management review และ Nonconformity/Corrective action ที่มีหลักฐานปิด

ไม่ยืนยันว่าองค์กรไม่มีเอกสารเหล่านี้ แต่ยังไม่ใช่ข้อมูลที่ Byakugan ชุดนี้รวบรวมและยืนยันได้

## สิ่งที่ควรทำก่อนส่งออดิต

1. ให้เจ้าของ ISMS ระบุขอบเขตเครื่อง ระบบ และช่วงวันที่ที่ออดิเตอร์ต้องการ เทียบทะเบียนกับ Agent/Monitor
2. ตรวจ Last seen, Snapshot, Log source และงานสแกนที่สำเร็จของทุกเครื่อง แยก Failed/No data/Out of scope ให้ชัด
3. ตรวจรายการที่ยัง OPEN/ACKNOWLEDGED, Owner, Due date, Risk acceptance และผลทดสอบยืนยันหลังแก้ ห้ามล้างเพื่อทำให้รายงานดูสะอาด
4. เชื่อม Backup/Restore และ Incident เข้ากับทะเบียนสินทรัพย์ด้วยรหัสถาวรในระยะถัดไป ปัจจุบันเก็บหลักฐานกลุ่มนี้จาก Export ทั้งหมดและให้ออดิเตอร์ตรวจเจ้าของประกอบ
5. เตรียมเอกสารภายนอกข้างต้น ตรวจ Mapping กับ SoA ที่อนุมัติ และเก็บไฟล์หลักฐานพร้อม SHA-256 ในที่จัดเก็บที่กำหนดสิทธิ์

## Export ใหม่: Excel ไฟล์เดียว

หน้า **ออดิตและ ISO 27001 → Export หลักฐานเซิร์ฟเวอร์ — Excel ไฟล์เดียว** เลือกช่วงวันที่ออดิตด้านบน แล้วเลือก `ทั้งหมด`, `Agent รายเครื่อง` หรือ `Monitor รายตัว` และกด **Export Excel ครบชุด**

มี 26 ชีท: สรุปและขอบเขต, ความครอบคลุมและสิ่งที่ขาด, เซิร์ฟเวอร์, ประวัติสินทรัพย์, CPU/RAM/Disk/Container, มอนิเตอร์, ประวัติตรวจบริการ, ฐานข้อมูล, รายการดำเนินการ, ช่องโหว่, งานสแกน, ผลสแกน, นโยบาย Health, สถานะ Health ล่าสุด, ประวัติ Health, เหตุการณ์, บันทึกเหตุการณ์, ส่งแจ้งเตือน, หลักฐานสำรอง, ทดสอบกู้คืน, เชื่อมโยงมาตรการ, ประวัติออดิต การล้างข้อมูล ช่วง WebSocket ขาด นโยบายสำรอง และส่งรายงาน/WORM

- เลือกรายเครื่องใช้ Agent ID จริง ไม่เดาความสัมพันธ์กับ Monitor/Backup จากชื่อ ชีทที่เชื่อมไม่ได้แสดง `NOT_LINKED_TO_SCOPE`; Backup/Restore และ Audit trail กลางรวมเมื่อเลือกทั้งหมด
- Health policies เป็น Config กลางที่ใช้ประกอบการอ่าน ส่วน Health state รายเครื่องกรองด้วย Subject key ที่มี ID
- เวลาข้อมูลคงเป็น UTC ตามต้นทาง ช่วงวันที่นับ 00:00–23:59 UTC; สถานะปัจจุบันและ Config เป็นค่าขณะ Export ไม่ใช่สถานะย้อนหลัง ณ วันสิ้นงวด
- `NO_ROWS` ไม่ใช่ผล “ผ่าน”; `EVIDENCE_PRESENT_REVIEW_REQUIRED` หมายถึงมีแถวให้ตรวจ ไม่รับรองคุณภาพหรือความครบถ้วน
- `EXTERNAL_EVIDENCE_REQUIRED` คือเอกสาร/หลักฐานที่ต้องเตรียมประกอบจากนอกระบบ
- จำกัด 25,000 แถวต่อชีทและรวม 150,000 แถว หากเกินจะไม่ส่งไฟล์บางส่วน ให้ลดช่วงเวลาหรือเลือกเครื่อง; เซลล์เกิน 32,767 ตัวอักษรจะแจ้งข้อผิดพลาด
- ไม่ส่ง Password, Token, Secret config หรือเนื้อหาที่พบเป็น Secret จากงานสแกน แต่ Log อาจมีชื่อผู้ใช้/IP/รายละเอียดเหตุการณ์ ต้องจัดสิทธิ์ไฟล์ตามนโยบายข้อมูลขององค์กร
- SHA-256 ที่หน้าจอใช้ตรวจว่าไฟล์ตรงกัน ไม่ใช่ลายเซ็นดิจิทัล ไฟล์นี้เป็นรายงานอ่านสะดวก; เมื่อต้องตรวจ Hash chain จากข้อมูลดิบให้ใช้ Evidence ZIP/หลักฐานต้นทางเพิ่ม
- เฉพาะ ADMIN/OPERATOR/AUDITOR ส่งออกได้ การ Export บันทึกขอบเขต จำนวนแถว และ SHA-256 ลง Audit trail

## แหล่งอ้างอิงหลัก

- [ISO: ISO/IEC 27001:2022](https://www.iso.org/standard/27001) — อธิบาย ISMS และมุมมองคน นโยบาย และเทคโนโลยี
- [IEC: ISO/IEC 27001:2022](https://webstore.iec.ch/en/publication/79694) — ข้อกำหนด ISMS รวมการประเมินและจัดการความเสี่ยง และไม่ยกเว้นข้อกำหนดหมวด 4–10 เมื่ออ้างความสอดคล้อง

การจัดหลักฐานขึ้นกับขอบเขตและความเสี่ยงขององค์กร ควรตรวจรายการสุดท้ายกับ SoA และออดิเตอร์ที่รับผิดชอบ
